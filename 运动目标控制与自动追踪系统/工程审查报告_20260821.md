## 三、未实现项清单(对照题目逐条)

### 3.1 未实现(完全缺失)

1. **绿色光斑位置控制系统(发挥部分核心)**
   - 题目要求:绿色激光笔固定在独立二维云台上,自动追踪红色光斑
   - 现状:工程里**没有任何绿色激光相关代码**(grep "green/GREEN/绿/追踪" 无结果),只有 `RED_LASER` 一个激光结构体
   - 影响:发挥部分(1)(2)完全无法得分(35 分 + 10 分)
2. **自动追踪算法**
   - 现状:OpenMV 只有红点识别+发送坐标,STM32 侧没有根据红点坐标驱动绿激光云台的逻辑
   - 需要:绿激光云台 PID 闭环(红点像素坐标 → 绿云台角度)
3. **追踪成功/失败判定 + 声光提示**
   - 题目要求:追踪成功发连续声光提示;两光斑距离 >3cm 记追踪失败
   - 现状:无蜂鸣器/声光相关代码,无判定逻辑
4. **暂停键功能**
   - 题目要求:红绿光斑应立即制动,以便测量两光斑中心距离
   - 现状:K1-K4 只是模式切换/标定,无暂停制动逻辑
   - 注意:key.c 中 K3 注释写了"暂停启动键",但实际是"开启模式2(A4 黑框)"
5. **红绿双系统独立运行**
   - 题目要求:红、绿系统相互独立、不得通信
   - 现状:只有一个控制链(红),绿侧不存在

### 3.2 部分实现(能用但有风险)

## 四、隐藏 BUG 清单(按严重程度排序)

### 🔴 P0 级(必须修,会导致实物跑错)

#### BUG-1:`Black_Retany` 数组初始化缺元素,数组越界读垃圾值

```c
// contorl.c:11 —— 第 4 个元素缺失!
int Black_Retany[4] = {47, 46, 94, };   // ← 只有 3 个初值,Black_Retany[3] = 未定义(实际=0)
```

- **影响**:`Motion_TarCtrl_Black()` 状态 4/5 大量使用 `Black_Retany[3]`(如 line 799),若 OpenMV 未成功回传 A4 四角坐标,黑框第 4 个角 y 坐标恒为 0,巡线到第 4 段会直接画向屏幕边缘 → 基(3)(4)脱胶
- **触发条件**:OpenMV 识别失败(未发 `p1..p8`)或未标定时直接按 K3
- **修复**:`int Black_Retany[4] = {47, 46, 94, 47};` 补齐第 4 个值(或用已有角点推算)

#### BUG-2:大框 `Motion_TarCtrl()` 的 `Box_Square_State` 不初始化 `FSTATE`

```c
// contorl.c:234 —— 只切 Laser_State,没设 FSTATE
case Box_Square_State:
    RED_LASER.Laser_State = Any_Rectang_Box_State;
    break;
```

- **对比**:黑框 `Motion_TarCtrl_Black()` 的 `Box_Square_State`(line 722-734)会设置 `Flag.FSTATE = Centy_To_Start`
- **影响**:若 `Flag.FSTATE` 残留上次运行结束值(如 `Fourth_To_End`),再按 K2 进入大框模式时,会从"第 5 段(第四点→起点)"开始算,而不是从中心起步 → 走线起点错乱
- **触发条件**:跑完一次大框后,不重新上电直接再按 K2
- **修复**:在 `Box_Square_State` 里补 `Flag.FSTATE = Centy_To_Start;`(与黑框一致)

#### BUG-3:`calculateSlope` 竖边返回 0 后,`calculateX` 除零/截断的边界行为

- 现状:竖边 `dx==0` 时 `calculateSlope` 返回 `0.0f`;随后若驱动轴选错为 X(`calcY` 恒等),或 `calculateX` 遇到 `slope==0` 返回 0(line 219)
- **注意**:`Motion_TarCtrl_Black` 状态 2/4 的竖边(`dx==0`)分支有 `if(Flag.dx != 0)` 注释声称守卫,但**实际代码里没有这个 if 守卫**(注释与代码不符)——见 BUG-4

#### BUG-4:竖边守卫注释与代码不一致(疑似被删)

```c
// contorl.c:199 注释说"由各 *_Y_* 分支 if(Flag.dx!=0) 守卫保持 x 为常量"
// 但实际 *_Y_* 分支:
case Centry_Y_Start_State:
    Flag.y_actual += BIG_FRAME_STEP;
    // ← 没有 if(Flag.dx != 0) 守卫!
    if(myabs(Flag.y_actual - RetangleY[0]) < 4) { ... }
```

- 全工程 grep `dx != 0` / `if(Flag.dx` 无结果 → **注释声称的守卫并不存在**
- **影响**:竖边(dx==0)若走 Y 驱动,`calculateX` 在 `slope==0` 时返回 0(line 219),`x_actual` 会被置 0 → 光斑跳到 x=0 → 彻底脱轨。固件里竖边分支是否走到取决于选轴规则(`|dx|>=|dy|` 选 X;竖边 dx=0 < |dy| 会选 Y 驱动),所以**竖边必然选 Y** → 存在风险
- **验证**:与 `sim/analysis/sim_firmware_consistency_check.py` 的竖边处理逻辑对照,该脚本明确区分"固件竖边=inf/UB,仿真=0.0,单独处理" → 说明竖边是已知薄弱点
- **修复**:在 Y 驱动分支补回 `if(Flag.dx != 0) { Flag.x_actual = calculateX(...); }` 守卫,或让 `calculateSlope` 对竖边返回一个哨兵值而非 0.0f

### 🟠 P1 级(建议修,影响可靠性和精度)

#### BUG-5:`X_AXIS / Y_AXIS` 复位逻辑与舵机 PID 目标耦合混乱

```c
// main.c:127-135
if(Flag.Is_Mode_Set == 0) {       // 复位模式
    if(None == 0) {
        Flag.x_actual = Flag.x_centry;   // 直接把实际值拉回中心
        Flag.y_actual = Flag.y_centry;
    }
    else if(None) {
        Flag.Anglex = 0;   // 未识别到红点时把角度清零
        Flag.Angley = 0;
    }
}
```

- 定时器回调里 `Flag.Anglex = Position_PID_RealizeX(Flag.X_AXIS, Flag.x_actual)` —— 输入参数顺序是 (reality, target)?看 pid.c:`Position_PID_RealizeX(float reality, float target)` 里 `Bias = target - reality`,调用处传的是 `(Flag.X_AXIS, Flag.x_actual)`,即 reality=X_AXIS、target=x_actual。语义上"X_AXIS 是测量值、x_actual 是目标值"——与字面含义相反,容易误读
- **实际影响**:复位时如果 OpenMV 没识别到红点(`None==1`),直接 `Anglex=0`,舵机会猛地回中,而不是回原点 → 复位可能"回机械零点"而非"回屏幕原点",误差超标
- **建议**:复位应统一通过 PID 闭环把 `X_AXIS` 拉向 `x_centry`;不要直接写死 `Anglex=0`

#### BUG-6:`calculateIntercept` 对 `slope==0` 无特判,竖边截距错误

```c
// contorl.c:206 —— 注释说"slope=0 时返回 0",实际没有特判
int calculateIntercept(int x1, int y1, float slope) {
    return (y1 - slope * x1);   // slope==0 时返回 y1,不是 0
}
```

- 注释与代码不符(注释声称 `if(slope==0) return 0;`,实际没有该分支)
- 竖边 slope=0 → intercept=y1,这实际上是"合理"的(截距=起点 y),但如果有人按注释预期用 0 值会导致错误;属注释误导

#### BUG-7:复位后 `Laser_State` / `FSTATE` 未重置,重复运行会错乱

- K1(复位)只改 `Is_Mode_Set=0`,**不重置 `RED_LASER.Laser_State` 和 `Flag.FSTATE`**
- 若在巡线中途按 K1 复位,再按 K2/K3 重新启动,状态机会从上次中断的位置继续 → 起点错乱
- **修复**:K1 复位时把 `RED_LASER.Laser_State = Box_Square_State; Flag.FSTATE = Centy_To_Start;`

#### BUG-8:按键无消抖/无防连按

```c
// key.c:3-22 Key_Scan 只读电平,Key_Proc 10ms 轮询但无消抖
```

- 快速连按或抖动会导致一次按键触发多次模式切换;实际比赛按键场景可接受,但建议加 20ms 消抖

### 🟡 P2 级(优化项)

#### BUG-9:OpenMV `find_redPoint` 每帧都调 `sensor.set_auto_exposure(False, 500)`

- 每次识别都改曝光参数,可能导致曝光反复抖动、帧率下降;建议移到初始化只设一次

#### BUG-10:红点阈值 `Red_threshold` 硬编码

- 不同环境光/不同激光笔亮度下可能误检或漏检;建议现场标定阈值或加自动增益

#### BUG-11:`clockwise_sort` 的极角排序方向

- `math.atan2` 升序排列得到的角点顺序是否真正"顺时针"取决于坐标系(y 轴向下时 atan2 输出与数学系相反),建议实测确认基(2)的走线方向是否真的顺时针,必要时取反

#### BUG-12:`Servo_Position_PIDX/Y` 的 `Ki=0`,积分项恒为 0

- pid.c: `Servo_Position.Ki = 0;` 且 `Integral_bias` 仍累加(做无用功),可删除或注释,避免误导

#### BUG-13:死区判定 `myabs(...) < 4` 在步长 7px 下可能越过目标

- 大框步长 7px > 死区 4px:若当前 x 与目标差 6px,一步 +7 变成差 1px(OK);若差 3px,一步 +7 变差 4px(不触发),再走一步差 11px → 永远不触发,靠 `if(d>prev_d) return best;` 兜底取最近点。逻辑上有兜底,但边界处可能多走一步 → 距边线误差可能略超 2cm 裕量
- 仿真 `gen_large_figs.py` 已证明 max=5px≈14mm < 2cm,✅ 可接受,仅提示

## 七、结论

1. **基本要求(2)(3)(4)主流程已实现**:大框/A4 黑框巡线、OpenMV 识别、标定流程齐全,仿真验证算术一致
